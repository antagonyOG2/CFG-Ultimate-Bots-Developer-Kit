# Architecture (current runtime)

This document describes how the mod works **today**, as an external DLL injected into the shipping game. It is the baseline the
CFG team will be replacing with native code; `INTEGRATION-GUIDE.md` maps each part to its native equivalent.

Facts below were verified by reading the files cited (snapshot commit `0f84e0ea`, release 1.0.0 built from H2.97). Paths are relative to
`Source/original-layout/`. Code snippets are short excerpts; pseudocode is labeled EXAMPLE.

## 1. Process layout

```
Player runs "CFG Offline Bots.exe"            Release/Launcher.cpp
   |  checks files + game SHA-256, backs up saves, starts Start_CampForestGreen.exe
   v
CFG-Offline-Bots-Loader.exe (hidden)          EventObserver/IntegrationHarness.cpp  --auto-install
   |  waits read-only until the player opens Offline Play, then installs ONCE per game launch
   v
Cfg35PrimaryGameplay.dll  (gameplay)          everything in Core/ + EventObserver/ (built with CFG_* defines)
```

* **Supported game binary:** `SummerCamp-Win64-Shipping.exe` SHA-256 `4FC4BB544747FFF85EA03DCB83DE0367AC2F5AF1AE5355614608C737E01A90A6`
  (CFG 3.5). Every native address is pinned to that exact image; other builds are refused (`RuntimeProbe/Compatibility/*.generated.hpp`,
  these address tables are withheld from the public kit; see WITHHELD.md).
* **Loader** (`IntegrationHarness.cpp` *(withheld from the public kit)*): command-line modes `--self-test`, `--install`, `--auto-install`, `--capture-all`,
  `--watch-menu`, `--hosted-match-state`. It verifies the pinned gameplay DLL path/size/SHA-256 (generated by
  `EventObserver/Write-*BuildPin.ps1` *(withheld from the public kit)*) before it touches the game. The release build uses `CFG35_RELEASE_PIN` so the helper is
  path-independent.
* The mod never modifies game files or save files; the launcher backs up `%LOCALAPPDATA%\CampForestGreen\Saved\{SaveGames,Config}` first.

## 2. Gameplay DLL bootstrap

1. The DLL is loaded into the game process and runs under a **frontend bundle** (`FrontendBundleRuntime.hpp`): it observes the menus,
   adds its own option rows (see section 9) and, when a match is created, initializes the **gameplay bundle**
   (`GameplayBundleRuntime.hpp`: `BundleAccess::Initialize`, `ServiceBundle`).
2. During bundle initialization (`GameplayBundleRuntime.hpp` near line 4895) the donor service is registered and the Jason tick hook is
   prepared:
   ```cpp
   bundleNativeJasonDonorService=&ServiceDonorNativeHunting;
   if(!PrepareNativeJasonControllerTick(plan.module)){ ... BundleStop(cfgbundle::Stop::Resources); }
   ```
   If the hook cannot be installed the whole bundle refuses to start rather than falling back to the old ProcessEvent AI.
3. `plan` is the per-match identity record (module base, thread id, world, mode, controller, pawn, object-array slots) that every proof is
   compared against.

## 3. Main driver: the native Jason controller Tick hook

The AI is driven from a detour on the game's **KillerAIController Tick** (`NativeJasonControllerTickRuntime.hpp`).

`BundleNativeJasonControllerTick(controller, deltaSeconds)` (the detour body):

1. Increment a depth counter; only depth 1 on the validated game thread may act.
2. `ResolveNativeJasonTickOwner(controller, owner)` decides if `controller` is the **primary** Jason's (`bundleJason`) or the **F1
   additional** Jason's (`bundleAdditional`, stage Active) controller. Everything else runs the unmodified original Tick.
3. `cfgjasontick::ObserveOwner(...)` re-proves the owner (identity serials, world, possession) and the code bytes of the base tick are
   checked (`BundleNativeJasonControllerTickCodeCurrent`).
4. `ObserveJ21NativeHints` reads water / held-victim state to choose between the **base** Tick (`BaseAIControllerTick`) and the full
   original Tick: owned controllers run the inherited/base Tick, THEN the donor driver; "never run both".
5. `ServiceNativeJasonControllerTick(owner)` (declared at line 58) runs only after the original/base tick returned:
   * opens `NativeJasonControllerTickSession` (lifetime/proof scope for this callback);
   * opens lookup/objective eligibility scopes and a `BundleCallbackRootScope` (GC roots, section 6);
   * hosted-only housekeeping (class restore at match end, host view repair);
   * finally calls `bundleNativeJasonDonorService(owner)` = `ServiceDonorNativeHunting`.
6. `ServiceDonorNativeHunting` (`DonorJasonHuntingService.hpp`, line 26) picks the primary or additional state, advances the
   **decision frame** (`DonorJasonDecisionFrame.hpp`; the target list is collected across several callbacks because a big roster does
   not fit one read budget) and, via `DonorNativeDrivePrimary` (`DonorJasonHuntingHostMembers.hpp`, line 450), runs the donor tick
   template `cfgdonorhunt::DonorRunOfflineBotsControllerTickOnGameThread(host)` (`Core/DonorJasonControllerTick.hpp`):

   ```
   if startup-trap setup active:  (slash once) / RunJasonAIStartupTrapSetup; return
   if door-break in progress:     Tick it; return
   if knife sequence active:      RunJasonAICombat; return
   chase update (DonorJasonChase) ; return if nav ring pending
   RunJasonAICombat               ; (owns attack release and held-victim input)
   read driver blocking states;   if blocked return
   call the verified driver slot (stock AI driver call)
   ```

The primary and the F1 Jason share the same Core templates; the F1 hunt state is `cfgdonorhunt::AdditionalHuntState`
(`DonorAdditionalJasonHunt.hpp`, function `DonorFrozenBridgeDriveAdditionalJason`).

Movement itself is a reflected UFunction call: `DonorIssueStockReflectedJasonMoveToLocationOnGameThread` (`Core/DonorJasonMovement.hpp`)
calls the controller's `MoveToLocation` with acceptance radius 85 cm, pathfinding/project-to-navigation/allow-partial true; result `2`
(request successful) updates `LastAcceptedMoveAt`.

## 4. ProcessEvent paths

Not every feature has a native entry point to hook. Many run inside a **returned host callback**: an engine `ProcessEvent` call that the
DLL observes (for example the local pawn's `ReceiveTick`, menu widget events, `UserWidget` events through a bridge) and during which a
root lease (section 6) is open. Work done there: F1/F3 key edges, menu row construction, the hosted sampler, spectator view, emotes.
Reflected calls the mod makes to the game also go through ProcessEvent (`host.Invoke(cdo, function, &packet)` pattern in
`AdditionalJasonBirthMembers.hpp`, `FeatureFunction(...)`, `SafeMoveToLocation`). These are replaced by direct C++ calls or Blueprint nodes in a native port.

## 5. Bundle report struct

`cfgbundle::Report` (`Core/GameplayBundlePolicy.hpp`, `ReportMagic=0x43464742`, `ReportVersion=87`, fixed size, seqlock-style `generation`
counter) is a plain struct in the DLL that an external tool reads to capture what the AI did. It holds hundreds of counters (spawns,
knife stages, car stages, convergence, burst starts, unstick escapes, kill hits/gates, callback timing). It is the basis of the parity
checks in `INTEGRATION-GUIDE.md` section 15. It is diagnostic only: it has no gameplay authority and a native port can replace it with
UE4 logging / stat counters.

## 6. GC callback root leases

The DLL is outside Unreal's reflection system, so UObjects it holds can be collected or recycled. The retention layer:

* `ResidentRootBank` / `PermanentRootPool`: slots registered with the collector.
* `cfgretain::CallbackRootLease` (`CallbackRootLease.hpp`): lifetime of **one completed engine callback**. `Retain` claims objects,
  `PrepareCall` / `EnterNative` / `CompleteCall` bracket every native call that can allocate (an "entered native" call makes all earlier
  proofs stale), `Close` releases. `ProvenSinceLastNative` lets a later step skip re-proof when no native call has occurred since (H2.92).
* `BundleCallbackRootScope` (`BundleCallbackRootsRuntime.hpp`) opens such a lease at the start of each Jason tick service.
* Identity: every object is referenced as `SlotObservation{object, index, serial}`; `SameSlot` re-reads the object array.

All of this exists only because of the external-DLL design. See `PORTING-STATUS.md`.

## 7. Offline vs hosted authority

Two independent modes share the Core policies but differ in who owns the Jason:

| | Offline | Hosted online |
|---|---|---|
| Jason pawn/controller | the game's normal offline "Jason bot" / spawned by the mod (F1) | the host's Jason slot is **adopted** (`HostedAdoption.hpp`, `HostedJasonTakeover.hpp`) |
| Authority predicate | `bundleStarted` + `bundleSchedule.active` | `HostedRoutineActive() == hostedRoutineStarted && HostedAdoptionOwnsDriver()` (`HostedJasonState.hpp`) |
| Match init | `BundleAccess::Initialize` | `InitializeHostedRoutine` (`HostedRoutineRuntime.hpp`) with nine numbered clauses |
| F1 birth | SpawnActor pawn + SpawnActor KillerAI controller + Possess | `HostedF1Birth` : SpawnActor at a native `SCKillerPlayerStart` + Possess (never RestartPlayer) |
| Bots | helper pipeline | hosted fill (`HostedFillRuntime.hpp`) |

Joiners are vanilla; the host is the server, so all AI lives on the host.

## 8. Feature flags

Each behavior is behind a `CFG_*` macro, default-valued in `Core/J22FeatureFlags.hpp` (59 flags) and the other `*FeatureFlags.hpp` headers
(`Documentation/FEATURE-FLAGS.md`). Flags were used to batch features per test build and to turn unproven features off for release
(`CFG_F1_CAR=0`, `CFG_H269_CHAT_MOVE=0`, `CFG_J23_BOT_NEAR_FOLLOW=0`, `CFG_J23_BOT_MELEE_ASSIST=0`, `CFG_J22_END_SUMMARY=0`,
`CFG_J22_CHALLENGE_REPLAY=0`).

## 9. Menus

`FrontendBundleRuntime.hpp` adds rows to the game's own settings widget through the row engine in `NativeSetupRows.hpp`
(`rows::Spec`: id, title, selected, labels, count). Offline rows: counselor skill, number of counselors, Jason difficulty, match length,
starting weapon, starting inventory, and practice toggles. Hosted rows (`HostedSettingsSpecs.hpp`): Jason bot on/off, difficulty, fill
empty slots, number of Jasons. Choices are stored per process (`cfghostedoptions::Store`) and snapshotted once per match
(`cfghostedoptions::Match::Capture`) so a menu edit cannot change a birth in flight.

## 10. Match lifecycle

* New match -> `ResetBundleWorldState(now)` clears donor-lane state; `BundleResetEpoch()` (`GameplayEpochReset.hpp`) retires a whole epoch.
* Offline -> hosted in one session: `HostedH1Runtime.hpp` runs `LeftoverEpochDecision` (H2.75/H2.93) once per hosted world.
* Hosted routine start also clears startup-trap progress and trap sources left by an offline match (`CFG_H293_HOSTED_TRAP_RESET`).
* F1 press in a new world clears the previous match's F1 state (`CFG_H286_F1_NEW_MATCH`, `GameplayBundleRuntime.hpp`).
